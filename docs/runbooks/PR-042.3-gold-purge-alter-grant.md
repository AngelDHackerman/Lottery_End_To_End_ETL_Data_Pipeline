# PR-042.3 — The swap could not alter the table it was built to alter

**Unplanned fix, not a roadmap item.** Found on 2026-09-24, on the first run that ever
reached PR-042.1's swap in production.

```
AccessDeniedException: Insufficient Lake Formation permission(s):
Required Alter on gold_winning_number_frequency
  File "/var/task/purge_and_load.py", line 420, in promote
    glue.update_table(DatabaseName=database, TableInput=_table_input(staged, table))
```

---

## 1. PR-042.1 changed the Lambda's job and left its grant describing the old one

Before PR-042.1 the gold-purge Lambda dropped each published table so a CTAS could rebuild
it in place. `DESCRIBE` + `DROP` was the exact right grant for that.

PR-042.1 replaced it with a blue-green swap: build `<table>__stg_<run>` beside the live
table, then repoint the published table at it with `glue.update_table`. **Lake Formation
governs that with `ALTER`, on the table.** The PR touched `modules/iam` and
`modules/orchestration`; it did not touch `modules/lake-formation`, so the grant still
described a job the code no longer did.

### The permission that looked like it was already there

The role *does* hold `ALTER` — at the **database** level:

```
$ aws lakeformation list-permissions \
    --principal DataLakePrincipalIdentifier=arn:aws:iam::913524903233:role/lottery-gold-purge-role-prod \
    --resource '{"Database":{"Name":"lottery_santalucia_db"}}'
[["ALTER", "CREATE_TABLE", "DESCRIBE", "DROP"]]

$ ... --resource '{"Table":{"DatabaseName":"lottery_santalucia_db","TableWildcard":{}}}'
[["DESCRIBE", "DROP"]]
```

Database `ALTER` authorises altering **the database** — renaming it, changing its
properties. It does not reach the tables inside it. Two grants, same word, different
resource. That database grant is also **not in Terraform state**: it was made out of band,
so no plan would ever have shown the gap.

## 2. Why it took five weeks of green runs to appear

| Date | What happened |
|---|---|
| 2026-09-17 | Last run under the OLD design. `gold_*` tables show `CreateTime == UpdateTime` and `CreatedBy = sfn-lottery-execution-role` — created, not altered. The Lambda never called `update_table`. |
| 2026-09-20/21 | PR-042.1 merged and applied. The swap is live in the Lambda. |
| 2026-09-24 18:00 | The scheduled run dies at the extractor (scrape.do outage → PR-031.2). Gold is never reached. |
| 2026-09-24 21:04 | Recovery run reaches the swap for the first time and dies on `ParamValidationError` → PR-031.3. |
| 2026-09-24 22:13 | With that fixed, the call finally reaches AWS — and Lake Formation refuses it. |

**The swap has never completed a production run.** Both defects sat in the same untested
path, and the scraper outage is the only reason they surfaced an hour apart instead of on
two separate Thursdays.

## 3. What changed

`modules/lake-formation/main.tf`, one line:

```diff
-  permissions = ["DESCRIBE", "DROP"]
+  permissions = ["ALTER", "DESCRIBE", "DROP"]
```

`ALTER` also covers the partition moves the swap makes after the repoint —
`batch_create/update/delete_partition` are catalog metadata on the table, not row-level
`INSERT`/`DELETE` — so those three are the whole set. Still not `["ALL"]`: Lake Formation
expands it server-side and reads it back expanded, which never settles (see the module
README).

The module README also gained the three gold rows it never had; PR-022 added those grants
and left the table documenting only the crawler's.

## 4. Apply

Pure infrastructure — no build, no artifact upload:

```bash
terraform -chdir=terraform plan     # measured: 1 to add, 0 to change, 1 to destroy
terraform -chdir=terraform apply
```

**The plan says "must be replaced", and that is normal.** A Lake Formation grant cannot be
modified in place — Terraform revokes the old one and grants the new one, so the resource
shows as `1 to add, 1 to destroy` rather than a change. There is a brief window mid-apply
where the role holds no table grant at all. Harmless here because nothing else runs
concurrently, but do not start a pipeline execution during the apply.

**Allow a few minutes for Lake Formation propagation** before re-running the pipeline; an LF
grant is not always effective the instant the API returns.

## 6. Left behind, and safe

Six staging tables from the two failed runs
(`__stg_recovery_415_norender_1790294279`, `__stg_post_apply_1790298383`) with data under
`gold/<table>/run=<run>/`. They are disposable: the swap deletes the staging catalog entry
last, precisely so a failure leaves it available to inspect, and each run's `prepare` empties
its own staging prefix. The published tables are all still on the 2026-09-17 generation —
consistent, one generation stale. Nothing is half-swapped, because `promote` failed on its
first call, before any partition moved.

## 7. The pattern worth naming

Three failures in one evening, three systems, one shape: a **contract with something
outside this repo** that was treated as settled. Cloudflare's tolerance for headless
rendering (PR-031.2), Glue's table schema (PR-031.3), and here a permission model where the
same verb means different things at two levels. The repo's own code was correct in all three
cases.

The actionable version: **a change to what code DOES is a change to what it must be
PERMITTED to do.** PR-042.1 reviewed its own logic thoroughly and never asked whether the
role could still perform the new operation. Grants belong in a change's blast radius
alongside the modules it edits.
