# PR-042.2 — Retire old Gold generations

Closes fault B's other half. PR-042.1 made publication atomic by building each gold table
beside the live one and swapping the catalog onto it; it deliberately left every previous
generation on disk. This adds the state that retires them, keeping the live generation plus
one so the rollback below always has a target.

**What this PR is not.** It is not a cleanup script. The three dead generations sitting in
`gold/` today are *arrears* that this mechanism collects on its first run — see §6 — and the
reason they could not simply be deleted by hand is itself the argument for building it here
rather than anywhere else.

the kind of claim a reviewer should want checked rather than assumed — and it is true here
only because the blast radius of this action is a strict subset of what `prepare` already
had.

---

## 2. The three safety properties, and where each one is enforced

Read these before the apply. They are the whole review.

**1. It runs after the swap.** `RetireGold` sits after `PromoteGold` in the Map iterator. A
delete that runs *before* the swap is precisely fault B, and putting retention earlier would
reintroduce it one state later. Enforced by the state machine, not by the Lambda.

**2. It cannot fail the run.** `RetireGold` carries `Catch: States.ALL → GoldRetentionSkipped`
(a `Pass`). By the time it runs, the published tables are already correct — there is nothing
left worth aborting for, and a leaked generation costs cents against a failed execution's
week of stale Gold.

**3. It never deletes the live generation.** The live location is read from
`glue:GetTable` **at the moment of the delete**, never from the event payload — even though
`promote` returns exactly that value one state earlier. A payload can go stale through a
retry or a future reordering of states; the catalog cannot. The live prefix is then excluded
by identity *and* by rank, and there is a redundant assertion at the point of deletion.

---

## 3. How "oldest" is decided

By the **newest object mtime** under each `run=` prefix, not by the run slug. A scheduled
execution is named by two UUIDs, so slugs carry no chronological order at all — ranking by
name would retire generations in effectively random order and could keep two dead ones while
deleting the only good rollback target.

Ties (two generations written in the same second) break on the prefix name, purely so the
choice is *reproducible*. Which of two same-second generations survives is arbitrary; that
it is the same one on every invocation is not, because an operator following §5 needs the
previous generation to still be there when they get to it.

## 5. Rollback — re-point the catalog at the previous generation

This is what `gold_keep_previous_generations = 1` exists to make possible. Per table:

```bash
DB=lottery_santalucia_db
TABLE=gold_draw_summary

# 1. What is live now, and what is still on disk behind it.
aws glue get-table --database-name $DB --name $TABLE \
  --query 'Table.StorageDescriptor.Location' --output text
aws s3 ls s3://lottery-partitioned-storage-prod/gold/draw_summary/

# 2. Re-point the table at the previous run= prefix. Fetch, edit the Location, put back:
#    UpdateTable replaces TableInput wholesale, so it must be built from the current table
#    rather than written from scratch, or you will drop its columns and SerDe.
aws glue get-table --database-name $DB --name $TABLE --query 'Table' > /tmp/t.json
# edit /tmp/t.json: StorageDescriptor.Location -> the previous run= prefix,
# then strip the read-only keys (DatabaseName, CreateTime, UpdateTime, CreatedBy,
# IsRegisteredWithLakeFormation, CatalogId, VersionId, IsMaterializedView).
aws glue update-table --database-name $DB --table-input file:///tmp/t.json
```

**For the three partitioned tables (`geo_winnings`, `vendor_leaderboard`, `time_series`) the
table is only half of it.** Athena resolves a partitioned table through its partitions, so a
table re-pointed without its partitions still serves the generation you were rolling back
*from*. That exact state — table on one generation, partitions on another — is what PR-042.4
produced in prod on 2026-09-24. Move them with `batch-update-partition`, and note that IAM
authorises that call against the **singular** `glue:UpdatePartition`.

**Do not roll back by deleting the live generation.** Re-point the catalog; leave the bytes.
A rollback that deletes is the failure mode this whole sub-phase exists to prevent.

## 6. The arrears this collects, and why they were not swept by hand

As of 2026-09-27 `gold/` holds the live generation plus **three dead ones** (16 objects) from
the failed runs of 2026-09-24: `recovery_415_norender_1790294279`, `post_apply_1790298383`
and `verify_alter_1790300025`. Their nine orphaned `__stg_` catalog entries **were** swept by
hand that day (`aws glue delete-table`); the bytes were not, and could not be:

- **PR-002's `Phase0DenyDeleteExceptRoot` exempts exactly two principals** — the account root
  and `lottery-gold-purge-role-prod`. An `AdministratorAccess` user is denied, because an
  explicit bucket-policy `Deny` is not something an IAM `Allow` can outvote.
- **The Lambda had no action that would.** `_empty_prefix` existed as a helper, but only
  `prepare` and `promote` were reachable through the handler.

So the leaked bytes were not cleanable **until this PR existed**. The guardrail was working
exactly as designed, and the exempted role is the one `RetireGold` runs as. Do not widen that
Deny's exemption list to sweep them; run the pipeline.

**On the first run after this applies**, each table retires down to live + 1. Verify:

```bash
for t in draw_summary winning_number_frequency terminations letters_distribution \
         geo_winnings vendor_leaderboard time_series; do
  echo "--- $t ---"
  aws s3 ls s3://lottery-partitioned-storage-prod/gold/$t/
done
# expect at most 2 run= prefixes per table (plus the flat layout — see below)
```

### The fourth thing on disk, which this mechanism deliberately cannot see

Under each table there is also the **pre-042 flat layout**: a bare Parquet at the table root
for the four unpartitioned tables, `year=*/` prefixes for the three partitioned ones, all
dated 2026-09-17. It does not match `run=`, so `retire` will never touch it.

That is a decision, not an oversight. It is the last generation that was *published and
good* before blue/green existed, and since every other non-live generation on disk came from
a run that **failed**, it is the only real rollback target today. It is reported in the
action's return value as `flatLayoutPresent` so it stays visible rather than becoming a
prefix nobody mentions.

**Retire it by hand once two healthy `run=` generations exist** — i.e. after the second
successful run following this apply, when the rollback target is a generation that was built
by the mechanism that is now in charge.

## 7. The alarm, and the deviation from the roadmap

`RetireGold` is designed never to fail the run, which means a retention failure leaves
**no trace in any service metric**: the execution reports `SUCCEEDED` and `ExecutionsFailed`
stays at zero. The Lambda's own `Errors` metric is shared with `prepare` and `promote`, whose
failures already fire alarm 1.

So alarm 7 is built on a **metric filter over the gold-purge log group**, grepping for the
literal token `GOLD_RETENTION_FAILED` that the handler emits on a retire failure and nothing
else emits.

> ⚠️ **The marker is an interface.** `RETENTION_FAILURE_MARKER` in `purge_and_load.py` and the
> `pattern` in `alarms.tf` must stay in step. Reword the log line and nothing fails — the
> alarm just silently stops firing forever. A test asserts the two match by reading the `.tf`
> file, because this project has already paid once for a monitor that disabled itself
> (PR-033.2).

**Deviation, stated rather than hidden.** The roadmap asks to "alarm on repeated failure".
This fires on the **first** one. With a weekly cadence, "repeated" means waiting a second
Thursday with no signal at all — and CloudWatch caps an alarm's total evaluation window at
seven days regardless (the same cap that forced alarm 2 down from eight days to seven). The
spirit of *"instead of blocking"* is kept exactly: the run is not failed, an email is sent.

## 8. Verify after the first real run

Per the lesson this sub-phase keeps re-learning: **a feature that changes which AWS APIs get
called is not reviewable from its own diff.** PR-042.1 was marked "applied + verified"
without ever getting a production run, and then failed three times in one evening on three
different permission gates. This needs one real run before it is called verified.

```bash
# 1. The run itself succeeded.
aws stepfunctions list-executions \
  --state-machine-arn arn:aws:states:us-east-1:913524903233:stateMachine:lottery-etl-pipeline-prod \
  --max-results 1 --query 'executions[0].{name:name,status:status}'

# 2. At most 2 run= generations per table (see §6 for the loop).

# 3. No staging entry left anywhere.
aws glue get-tables --database-name lottery_santalucia_db \
  --query 'TableList[?contains(Name, `__stg_`)].Name' --output text   # expect: empty

# 4. All 7 tables on ONE generation, and non-empty. "Successful swap, empty table" is
#    invisible until someone counts.
for t in gold_draw_summary gold_winning_number_frequency gold_terminations \
         gold_letters_distribution gold_geo_winnings gold_vendor_leaderboard gold_time_series; do
  aws glue get-table --database-name lottery_santalucia_db --name $t \
    --query "[\"$t\", Table.StorageDescriptor.Location]" --output text
done

# 5. The retention did not fail silently.
aws logs filter-log-events \
  --log-group-name /aws/lambda/lottery-gold-purge-prod \
  --filter-pattern '"GOLD_RETENTION_FAILED"' \
  --start-time $(( ($(date +%s) - 86400) * 1000 )) \
  --query 'events[].message' --output text     # expect: empty
```

Step 5 is the one that is easy to skip and is the entire point of the alarm: a green run
tells you nothing about whether this PR's state did its job.
