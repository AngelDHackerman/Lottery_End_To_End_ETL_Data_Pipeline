# PR-042.4 — `BatchUpdatePartition` is authorised against `UpdatePartition`

**Unplanned fix, not a roadmap item.** The third defect found in PR-042.1's swap on
2026-09-24, one run after PR-042.3.

```
AccessDeniedException: User: .../lottery-gold-purge-role-prod is not authorized to perform:
glue:UpdatePartition on resource: arn:aws:glue:us-east-1:913524903233:catalog
because no identity-based policy allows the glue:UpdatePartition action
  File "/var/task/purge_and_load.py", line 426, in promote
    partitions = _move_partitions(database, table, _all_partitions(database, staging_table))
  File "/var/task/purge_and_load.py", line 314, in _move_partitions
    resp = glue.batch_update_partition(
```

---

## 1. The policy already listed the Batch action. That is not what Glue checks.

`lottery-gold-purge-policy-prod` carried `glue:BatchCreatePartition`,
`glue:BatchUpdatePartition` and `glue:BatchDeletePartition`. The code calls
`batch_update_partition`. The denial still names **`glue:UpdatePartition`** — the singular
form. Glue authorises the Batch APIs **per item**, against the singular action.

The SFN role has carried `glue:CreatePartition` + `glue:UpdatePartition` since PR-009, which
is why the CTAS path never hit this and why the gap survived review: the same file contains a
working example fifteen lines away.

The fix adds the three singular actions and keeps the `Batch*` ones — Glue's own
documentation lists them, and dropping them on the strength of one error message would be
guessing in the opposite direction.

## 2. Two permission systems, two separate failures, same operation

PR-042.3 granted Lake Formation `ALTER`, which is what let `update_table` through. Its note
said ALTER "also covers the partition moves" — **true of Lake Formation, and only of Lake
Formation.** IAM is a second, independent gate on the same call, and it was never checked.
Both had to be right; each failure hid the next.

The general form, now demonstrated three times in one evening: **when an AccessDenied names
an action, read which system produced it.** `Insufficient Lake Formation permission(s)` and
`no identity-based policy allows` are different sentences from different services, and fixing
one tells you nothing about the other.

## 3. This failure was the first that MUTATED state

The two before it died before touching anything. This one died *between* the two halves of
the swap — after `update_table`, during `_move_partitions`:

| Table | Partitioned | State after the failure |
|---|---|---|
| `gold_draw_summary` | no | fully swapped ✅ |
| `gold_terminations` | no | fully swapped ✅ |
| `gold_winning_number_frequency` | no | fully swapped ✅ |
| `gold_geo_winnings` | **yes** (`year`, 3) | **half-swapped** — table repointed, partitions not |
| `gold_time_series`, `gold_letters_distribution`, `gold_vendor_leaderboard` | — | untouched, 2026-09-17 |

For the three unpartitioned tables `_move_partitions` is a no-op, so they swapped cleanly.
`gold_geo_winnings` is the inconsistency fault B exists to prevent: its table location points
at `gold/geo_winnings/run=verify_alter_1790300025/` while its three partitions still point at
`gold/geo_winnings/year=YYYY`.

**It is not corrupt, and it is not unreadable.** Athena resolves a partitioned table through
its PARTITION locations, so queries return the 2026-09-17 generation — stale, internally
consistent, and still on disk (verified: `year=2024/`, `year=2025/`, `year=2026/` all intact
beside the new `run=` prefix). The real defect is *across* tables: `gold_draw_summary` now
includes sorteo 415 and `gold_geo_winnings` does not.

**No manual repair is needed.** The next successful run rebuilds every table and its
`promote` moves the partitions, which is exactly the repair. Do not hand-edit the catalog.

The orphaned `run=` prefixes from the failed attempts stay on disk — each run's `prepare`
empties only its own staging prefix. Retiring old generations is PR-042.2, still `todo`.

## 4. Apply

```bash
terraform -chdir=terraform plan     # measured: 0 to add, 2 to change, 0 to destroy
terraform -chdir=terraform apply
```

The second change is `module.orchestration.aws_lambda_function.gold_purge`, and it is the
known phantom: `module.iam` gaining a change defers the `archive_file` data-source read, so
the Lambda shows a pending source hash it will resolve to the same value. No build or
artifact upload is needed.

IAM propagation is fast but not instant; give it a minute before re-running.

## 6. What PR-042.1 actually needed

Three fixes so far, all of them infrastructure, none of them logic:

| | Gate | Fix |
|---|---|---|
| PR-031.3 | botocore request validation | allowlist the fields `TableInput` accepts |
| PR-042.3 | Lake Formation | `ALTER` on the tables |
| PR-042.4 | IAM | the singular partition actions |

The swap's *code* has been right since 2026-09-20. Everything that broke sat in what the
code was permitted to do, and none of it could be seen without executing the path. **A
feature that changes which AWS APIs get called is not reviewable from its own diff** — it
needs one real run, and PR-042.1 was marked "applied + verified" without ever getting one.
