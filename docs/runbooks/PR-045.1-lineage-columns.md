# PR-045.1 — Lineage columns in Silver

Closes the writing half of **fault F**. Four columns on both Silver datasets, so a row can
be traced back to the run and the raw file that produced it.

| column | type | meaning |
|---|---|---|
| `run_id` | string | the PR-018 correlation id = the Step Functions execution name. **NULL when absent, on purpose** |
| `ingested_at` | timestamp | when the transformer wrote the file. UTC, timezone-**naive** |
| `source_key` | string | the `raw/` S3 key the row came from |
| `parser_version` | int | bumped by hand when the parse changes shape. Currently `1` |

The contract lives in one place, `src/loteria/common/lineage.py`, so the writer
(`transformer`), the suites (`dq.suites`) and the loader (`dq.runner`) agree by construction
rather than by three people remembering.

---

## 1. ⚠️ Read this first: Athena will NOT see these columns

**This was verified against the live account before the code was written, and it is the
reason PR-045.2 exists as a separate sub-PR rather than as polish.**

```
$ aws glue get-crawler --name lottery-sorteos-silver-crawler \
    --query 'Crawler.{Schema:SchemaChangePolicy,Recrawl:RecrawlPolicy,Config:Configuration}'
{
  "Schema":  {"UpdateBehavior": "LOG", "DeleteBehavior": "LOG"},
  "Recrawl": {"RecrawlBehavior": "CRAWL_NEW_FOLDERS_ONLY"},
  "Config":  "{\"CrawlerOutput\":{\"Partitions\":{\"AddOrUpdateBehavior\":\"InheritFromTable\"}}}"
}
```

Three settings compound, and each one alone is enough to hide the new columns:

1. **`UpdateBehavior: LOG`** — the crawler *detects* a schema change and only writes a log
   line. It does not alter the table.
2. **`CRAWL_NEW_FOLDERS_ONLY`** — it only looks at new partitions, never re-examines the
   existing ones.
3. **`Partitions.AddOrUpdateBehavior: InheritFromTable`** — a new partition is given the
   **table's** schema, not the schema of the files inside it.

So the four columns will be written into every new Parquet file and
`silver_sorteos_sorteos` will keep the same ten columns it has today. `SELECT run_id FROM
silver_sorteos_sorteos` will fail with a column-not-found error.

**That is expected and it is not a defect in this PR.** The tracker's split is `.1` write
them, `.2` make them queryable, and this is exactly the seam. What makes `.1` useful on its
own is that **the data-quality gate does not go through Athena** — `dq.runner` reads the
Parquet directly with boto3 + pandas, so the lineage expectations below are live from the
first run after the deploy, catalog or no catalog.

**Do not "fix" this by flipping `UpdateBehavior` to `UPDATE_IN_DATABASE` in passing.** With
`CRAWL_NEW_FOLDERS_ONLY` and `InheritFromTable` in play, the interaction needs deciding
deliberately — including whether the Silver table schemas should be managed in Terraform
instead of inferred by a crawler at all, which is the more defensible end state for a table
seven downstream CTAS queries depend on. That is PR-045.2's job.

## 2. The gate's lineage checks are conditional, and that is deliberate

Both suites gain four `expect_column_values_to_not_be_null` expectations, each gated on
`parser_version >= 1`.

**Why not unconditional.** The suites validate the *whole dataset*, which includes the 222
files written before lineage existed. An unconditional not-null on `run_id` would go red on
day one against perfectly good historical data — the fails-on-arrival trap PR-032 spent a
paragraph avoiding. A gate that is red on arrival teaches everyone to ignore the gate.

**Why a `parser_version` floor and not "where `run_id` is not null".** The latter is
circular: it would exclude exactly the rows the expectation exists to catch.

**What this buys.** `run_id is not null` on lineage-era rows is the only check in this
project that can notice **something wrote Silver outside the pipeline**. That is also why
`run_id` is left NULL rather than filled with `"manual"` or a hostname — a substituted value
would silently answer the question the gate is asking.

**Consequence to expect:** a hand-run transform without `CORRELATION_ID` set **will turn the
gate red**. That is correct. It did write Silver outside the pipeline.

**The transitional read.** `dq.runner.ensure_lineage_columns` adds the four columns as NA
when absent, because a pandas row condition raises on a column that is not in the frame —
and on day one, before a single new sorteo has been transformed, none of them are.

## 3. ⚠️ The Glue 3.9 ceiling, and why ruff will try to break it

`loteria/common/lineage.py` ships inside **both** deploy artifacts:

| runtime | Python | job |
|---|---|---|
| Glue Python Shell | **3.9** | `lottery-transform-prod` |
| Glue Spark (5.0) | 3.11 | `loteria-silver-dq-prod` |
| Lambda | 3.12 | `lottery-extractor-prod` |

`pyproject.toml` sets `target-version = "py312"`, so ruff's `UP` rules suggest constructs the
3.9 runtime does not have. Writing `utc_now()` the way ruff wanted (`dt.UTC`, a 3.11+ alias)
would have passed CI, imported fine on the Lambda, and raised `AttributeError` in the weekly
Glue run. Hence the `# noqa: UP017` with its reason attached, and
`TestTheGlueRuntimeCeiling` asserting the alias never reappears.

> **Latent hazard, not fixed here.** There are no `per-file-ignores` in `pyproject.toml`, so
> nothing stops the same suggestion being accepted in another `loteria/` module that Glue
> imports. The real fix is either a per-file ignore for the Glue-bound tree or leaving
> Python Shell for Spark (roadmap **Open later L6**). Flagged rather than done, because
> rewriting the repo's lint configuration does not belong in a PR about lineage columns.

## 5. Verify after the first real run

The columns only appear on sorteos transformed *after* the deploy, so this needs a pipeline
run. Nothing here goes through Athena — see §1.

```bash
# 1. The newest Silver file carries the four columns, with a real run_id.
KEY=$(aws s3 ls --recursive s3://lottery-partitioned-storage-prod/silver/sorteos/ \
        | sort -k1,2 | tail -1 | awk '{print $4}')
aws s3 cp "s3://lottery-partitioned-storage-prod/$KEY" /tmp/s.parquet
python - <<'PY'
import pandas as pd
df = pd.read_parquet("/tmp/s.parquet")
print(df[["run_id", "ingested_at", "source_key", "parser_version"]].to_string())
PY
# expect: run_id = the Step Functions execution name of that run, NOT null
#         source_key = the raw/ key it came from
#         ingested_at within minutes of the run
```

```bash
# 2. The gate passed WITH the lineage expectations live — not because it skipped them.
#    A green DQ run proves nothing on its own here: if the row condition had errored, the
#    expectations would be absent rather than failing.
aws logs filter-log-events \
  --log-group-name /aws-glue/jobs/loteria-silver-dq-prod \
  --filter-pattern '"run_id"' \
  --start-time $(( ($(date +%s) - 7200) * 1000 )) \
  --query 'events[].message' --output text | head
```

```bash
# 3. The old files were NOT rewritten. Lineage is additive; a backfill is a separate
#    decision and this PR deliberately does not make it.
aws s3 ls --recursive s3://lottery-partitioned-storage-prod/silver/sorteos/ | wc -l
# expect: previous count + 1, and the pre-existing objects' LastModified unchanged
```

## 6. What this PR deliberately does not do

- **No backfill.** The 222 pre-lineage files keep NULLs. A backfilled `ingested_at` is a lie
  and a fabricated `run_id` is worse than a null one — NULL correctly means "written before
  lineage existed", and it is greppable. The sentinel backfill stays a separate PR to be
  decided on its own merits.
- **No Gold changes.** `run_id` does not flow into the gold tables. Every file in
  `sql/gold/` names its columns explicitly — now asserted by
  `TestGoldCannotInheritSilverColumnsByAccident`, which is what keeps the *next* Silver
  column from leaking in unannounced. Whether `gold_draw_summary` should carry the `run_id`
  that built it is a real question and the roadmap recommends yes; it needs the catalog to
  expose the column first, so it belongs after PR-045.2.
- **No crawler change.** See §1.
