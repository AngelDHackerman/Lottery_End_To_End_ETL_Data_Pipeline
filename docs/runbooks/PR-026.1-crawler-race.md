# PR-026.1 — Fix the race between `startCrawler` and the gold CTAS

**Type:** correctness fix. Not deferred scope — the pipeline reports green today while
building gold from a stale catalog.

**Scope:** one resource changes, `aws_sfn_state_machine.pipeline_state_machine`. Nothing is
created or destroyed by this PR.

---

## 1. What was wrong

The state machine started the two silver crawlers with
`arn:aws:states:::aws-sdk:glue:startCrawler`. **There is no `.sync` variant of that
integration.** The task completed when the API call was *accepted*, so Step Functions moved
straight on to `PrepGold` → `BuildGold` and the 7 gold CTAS raced the crawls.

Measured on the 2026-07-30 run (`stepfunctions get-execution-history` timestamps against the
`BENCHMARK` lines in `/aws-glue/crawlers` — neither source shows this alone):

| Time (UTC-3) | Event |
|---|---|
| 15:01:48.9 | `RunSorteosCrawler` returns, SFN moves on |
| **15:02:02.2** | **first 2 `RunCTAS` start** (13 s later) |
| 15:02:09 | the sorteos crawl actually begins scanning |
| **15:02:55** | **"Finished writing to Catalog"** — catalog now current |
| 15:02:57 → 15:04:03 | the remaining 5 CTAS start |
| 15:06:34 | crawler reaches `READY` (3m39s of teardown after the catalog write) |

**Two of the seven CTAS ran 53 s before the catalog was updated.** Which two lose depends on
`Map` scheduling (`MaxConcurrency = 3`), so the affected gold table is non-deterministic.

Silver is partitioned by **`(year, sorteo)`** — 109 partitions each, verified live — so every
weekly run creates a **brand-new partition**, invisible to Athena until a crawler registers
it. This is *not* the "new files inside an existing partition" case Athena resolves on its
own.

Nothing looked broken because the 2026-07-30 run ingested no new sorteo (3130 was already
catalogued on 2026-07-26), so the two losing CTAS read a *correct* stale catalog. That is
luck. On a normal week the damage is silent: no failure, no alarm, a gold table missing the
newest draw until the next rebuild papers over it.

**PR-025 does not cover this.** Its crawler alarms fire when a crawl *fails*; here every
crawl succeeds.

## 2. What changed

`RunPremiosCrawler` + `RunSorteosCrawler` are replaced by one `Parallel` state,
`RunSilverCrawlers`, with a branch per crawler:

```
Baseline<X>Crawler   getCrawler   -> $.baseline
Start<X>Crawler      startCrawler, ResultPath null
Init<X>Poll          attempts = 0
Wait<X>Crawler       <---------------------------+
Get<X>Crawler        getCrawler -> $.current     |
Check<X>Crawler      Choice ---------------------+  (not done -> Increment<X>Poll)
Verify<X>Crawl       Choice on LastCrawl.Status
<X>CrawlSucceeded (Succeed) | <X>CrawlTimedOut (Fail) | <X>CrawlFailed (Fail)
```

Design notes are in `terraform/modules/orchestration/README.md`. The three that will bite
you if you edit this later:

1. **Polling for `State == READY` alone is not correct.** `READY` is also what a crawler
   reports in the window between `StartCrawler` returning and the control plane flipping it
   to `RUNNING`. The `Baseline` state captures `LastCrawl.MessagePrefix` (the crawl's UUID)
   first, and the completion test requires that prefix to have **changed**.
2. **A crawler that has never run has no `LastCrawl` block at all.** Not reachable in this
   account (100+ crawls each) but reachable for a fresh clone, so there is a dedicated
   Choice rule for it and every comparison is `IsPresent`-guarded — the pattern AWS
   documents for possibly-absent fields.
3. **`Verify<X>Crawl` is a behaviour change.** A crawl that finishes with
   `LastCrawl.Status != SUCCEEDED` now **fails the execution**; it used to let the pipeline
   finish green. A failed crawl leaves the catalog exactly as stale as no crawl.

**No IAM change is needed.** PR-009 already granted `glue:GetCrawler` next to
`glue:StartCrawler`, narrowed to the two silver crawler ARNs. Verified against the live
policy, not the code:

```bash
aws iam get-policy-version \
  --policy-arn arn:aws:iam::<acct>:policy/sfn-lottery-policy-prod \
  --version-id v7 \
  --query 'PolicyVersion.Document.Statement[?Sid==`AllowStartGlueCrawlers`]'
```

The roadmap prompt predicted a policy edit. It was already there.

## 4. Verification

### 4a. Before applying — validate the rendered ASL

The definition is generated by a `for` expression, so a typo becomes a runtime failure five
minutes into a weekly run. Validate it statically instead:

```bash
cd terraform
terraform plan -out=tfplan
terraform show -json tfplan > plan.json
python3 -c "
import json
p=json.load(open('plan.json'))
for rc in p['resource_changes']:
    if rc['address'].endswith('pipeline_state_machine'):
        open('asl.json','w').write(rc['change']['after']['definition'])
"
aws stepfunctions validate-state-machine-definition --definition file://asl.json --type STANDARD
```

Expected: `{"result": "OK", "diagnostics": []}`. This checks the `Choice` syntax,
`StringEqualsPath`, `IsPresent`, the `States.MathAdd` intrinsic and the `Parallel` shape —
all the parts that are easy to get subtly wrong.

### 4b. After applying — trigger one execution

```bash
aws stepfunctions start-execution \
  --state-machine-arn arn:aws:states:us-east-1:<acct>:stateMachine:lottery-etl-pipeline-prod \
  --name pr0265-verify-$(date +%s)
```

Then confirm **every** `RunCTAS` starts after **both** crawlers wrote the catalog:

```bash
# CTAS start times
aws stepfunctions get-execution-history --execution-arn <arn> --max-items 1000 \
  --query "events[?stateEnteredEventDetails.name=='RunCTAS'].timestamp"

# catalog write times
aws logs filter-log-events --log-group-name /aws-glue/crawlers \
  --log-stream-names lottery-premios-silver-crawler lottery-sorteos-silver-crawler \
  --filter-pattern '"Finished writing to Catalog"' \
  --query 'events[].{stream:logStreamName,t:timestamp}'
```

**Pass = min(CTAS start) > max(catalog write).** Under the old definition the first CTAS
preceded the catalog write by ~53 s.

Also confirm the branches actually polled rather than short-circuiting:

```bash
aws stepfunctions get-execution-history --execution-arn <arn> --max-items 1000 \
  --query "length(events[?stateEnteredEventDetails.name=='GetPremiosCrawler'])"
```

Expect **several** — a `1` would mean the first poll saw a stale `READY`, which is exactly
what the baseline check exists to prevent. If it is ever 1, re-read section 2 note 1.

#### ✅ VERIFIED IN PROD — execution `pr0261-verify-1786291620`, 2026-08-09

`SUCCEEDED` in 4m59s (13:07:01.5 → 13:12:00.8 UTC-3).

| Measurement | Result |
|---|---|
| Last catalog write (sorteos) | 16:08:42.100 UTC |
| Catalog write (premios) | 16:08:39.914 UTC |
| **First `RunCTAS`** | **16:09:04.466 UTC** |
| **Margin** | **+22.4 s AFTER the last catalog write** |
| `GetPremiosCrawler` polls | 2 |
| `GetSorteosCrawler` polls | 2 |
| `PremiosCrawlSucceeded` / `SorteosCrawlSucceeded` | 1 each |

**The defect is closed.** The same measurement on the pre-fix 2026-07-30 run had the first
CTAS starting **53 s BEFORE** the catalog write; it is now **22.4 s after**, a swing of ~75 s.
All 7 CTAS started after both crawlers had written.

Two polls per crawler (not one) is the important secondary result: the branches genuinely
waited rather than reading a stale `READY` on the first look.

**Latency came in cheaper than predicted.** §5 estimated ~4–5 min of added wall clock from
the crawler teardown before `READY`. The actual run was 4m59s total against a ~4m20s
pre-fix baseline — about **+40 s**, because `Parallel` overlaps the two waits and both
crawlers reached `READY` within two poll intervals.

### 4c. The real acceptance test — a run that ingests a new sorteo

Gold row counts only diverge on a week that adds a sorteo. After such a run:

```sql
SELECT MAX(numero_sorteo) FROM lottery_santalucia_db.gold_draw_summary;
SELECT MAX(numero_sorteo) FROM lottery_santalucia_db.silver_sorteos_sorteos;
```

They must be equal. Run these as **`angel-adming`** — the root user cannot query under Lake
Formation and gets a misleading `COLUMN_NOT_FOUND`.

#### ✅ VERIFIED 2026-08-09 (query `04673844-4f63-4ced-98a0-96d25319da4e`)

| `gold_max` | `silver_max` | `gold_rows` | `silver_sorteos` |
|---|---|---|---|
| **3132** | **3132** | **111** | **111** |

Exact agreement. And unlike the pre-fix check — which was inconclusive because the
2026-07-30 run ingested no new sorteo, so a stale catalog was still a *correct* catalog —
this one is meaningful: the counts moved from 109/3130 to **111/3132**, so new sorteos have
been catalogued since the fix and gold tracked them.

## 5. Cost / latency impact

- Adds roughly one crawl's wall clock (~4–5 min) to a weekly run, because `READY` lags the
  catalog write by ~3.5 min of crawler teardown. `Parallel` keeps that from being charged
  twice.
- ~100 extra state transitions/week (≈ $0.002) and up to 60 `GetCrawler` calls, which carry
  a narrow throttling retry.

## 6. Out of scope

Retries/`Catch` on the other states, PR-025's crawler-failure alarms, and any change to the
CTAS SQL.
