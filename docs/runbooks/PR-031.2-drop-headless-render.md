# PR-031.2 — Drop `render=true`: the August fix became the September outage

**Unplanned fix, not a roadmap item.** The weekly pipeline failed on 2026-09-24 at
`RunExtractorLambda`, 57.5 s in, with the same `502 / ErrorCode 90 / ROTATION_FAILED` that
PR-031.1 diagnosed five weeks earlier — except this time the cause was the parameter
PR-031.1 *added*. The fix is to stop sending `render=true`.

**Nothing is corrupt.** The run died at step 1, so Glue, the crawlers and the gold CTAS
never executed. The lake was simply one sorteo stale: raw and silver current through
Ordinario 3136 (ingested 2026-09-17); the 2026-09-03, 09-10 and 09-17 runs all SUCCEEDED.

**Read PR-031.1's runbook first if you have not.** This document only covers what changed
since; the cost model, the prize-markup story and the alarm inventory are all still there.

---

## 1. The symptom looks identical to August. The cause is inverted.

Production log, 2026-09-24 18:01:35 UTC:

```
[PROXY] https://loteria.org.gt/site/award -> HTTP 502 | Preview: {"URL":"...","StatusCode":502,
"ErrorCode":90,"ErrorType":"ROTATION_FAILED","Message":["Error: unexpected network failure",
"You're already using super=true and render=true. Occasional failures on protected domains
are expected.","Request failed and not charged. Please try again."]}
```

That middle sentence is the whole diagnosis: scrape.do is saying it has **nothing left to
escalate to**. In August the same error meant "you are not using enough"; here it means the
maximum profile is the one failing.

It is not transient, despite what the message suggests. Measured before changing anything:

| Attempt | Profile | Result |
|---|---|---|
| Scheduled run 18:00 UTC | GT + super + render | 502 ROTATION_FAILED, 57.50 s |
| Manual SFN run 20:39 | GT + super + render | 502 ROTATION_FAILED, 57.50 s |
| 5 direct probes 20:45–20:50 | GT + super + render | 502 × 5, 57.53–57.60 s, **byte-identical bodies** |
| Variant A | GT + super + render, site root | 502 ROTATION_FAILED |
| **Variant B** | **GT + super, NO render** | **HTTP 200 in 9.7 s, first try** |

Eight consecutive failures across three hours, then a 200 on the first attempt without
render. The remaining variants (MX/US/CR geos, no-geo, `blockResources`, `customWait`,
`waitUntil`, sticky `sessionId`, `regionalGeoCode`) were never needed.

**What has held across both incidents: `geoCode=GT` and `super=true`.** GT is
residential-only so `super` is not optional, and no other country has ever worked. Treat
those two as the floor and `render` as the dial.

### Diagnosis technique worth reusing

**Failed scrape.do requests are not charged.** The quota counter sat at exactly 1000/1000
through all eight failures. So probing variants costs nothing until one *succeeds* — which
is the outcome you want anyway. Do not reason about the profile from documentation; try
combinations until one returns 200, and stop there.

A local `curl` to `loteria.org.gt` returning **403 Cloudflare** is expected and proves
nothing about an outage — see the note in `docs/` on the second official site.

## 2. What changed

| File | Change |
|---|---|
| `src/loteria/extractor/scraping.py` | `SCRAPE_RENDER` default `"true"` → `"false"`; the profile note rewritten to carry both incidents |
| `terraform/modules/etl-lambda/variables.tf` | `scrape_render` default `true` → `false` |
| `tests/unit/test_scraping.py` | `test_requests_headless_rendering` → `test_does_not_request_headless_rendering`; new test that `SCRAPE_RENDER=true` still restores rendering |
| `tests/integration/test_scraper_contract.py` | canary profile flipped; omits a parameter instead of sending `false`; new `test_proxy_profile_matches_the_extractor` |

### The canary duplicated the profile by hand, and a comment was the only guard

PR-031.1 left `GEO_CODE` / `PROXY_RENDER` / `PROXY_SUPER` written out in two files with a
comment asking the next reader to keep them in sync. The canary cannot import
`scraping.py` — that module calls `get_secrets()` at import time and the canary must run in
GitHub Actions with no AWS credentials — so the duplication is structural. What was missing
was a check. `test_proxy_profile_matches_the_extractor` now reads the defaults out of the
source text and fails on drift, the same way `test_selectors_match_the_extractor` already
did for the six locators.

Without it, this PR would have left the canary sending `render=true` against the live site:
green or red, its verdict would have been about a request production no longer makes.

### The canary also sent `&render=False`

The old URL assembly interpolated the constant directly, so flipping it to a Python-style
value would have shipped `render=False` rather than dropping the parameter. `build_proxy_url`
in the extractor omits parameters that are off; the canary now does the same.

## 3. Cost — this got cheaper

`super=true` **without** render costs **10 credits** per request, versus 25 with it,
measured by diffing `RemainingMonthlyRequest` across each call. Two proxied calls per run:

| | Per request | Per pipeline run | Per month (~4.3 runs + weekly canary) |
|---|---|---|---|
| PR-031.1 profile | 25 | 50 | ~430 / 1000 |
| PR-031.2 profile | 10 | 20 | ~175 / 1000 |

The 2026-09-24 incident consumed **20 credits total** (one listing + one detail page,
both on the new profile). The eight failures cost nothing.

## 4. Apply

The Lambda reads `SCRAPE_RENDER` from its environment, so an incident can be resolved
before this PR merges — that is what happened here, at 20:55 UTC on 2026-09-24:

```bash
# Read the current environment, flip one key, write it back. update-function-configuration
# REPLACES the whole map — building the payload from the live config is what keeps the
# other eight variables from being silently dropped.
aws lambda get-function-configuration --function-name lottery-extractor-prod \
  --query 'Environment.Variables' --output json \
  | python3 -c 'import json,sys; v=json.load(sys.stdin); v["SCRAPE_RENDER"]="false"; print(json.dumps({"Variables":v}))' \
  > /tmp/env.json

aws lambda update-function-configuration --function-name lottery-extractor-prod \
  --environment file:///tmp/env.json
```

**That leaves prod drifted from Terraform until this PR is applied**, and the next
`terraform apply` would set `SCRAPE_RENDER` back to `true` and re-break the pipeline. Apply
this PR to close it. The expected plan is the env var plus the usual artifact churn.

## 6. Follow-ups filed, not fixed here

- **`RunExtractorLambda`'s `Retry` does not cover the failure that keeps happening.**
  PR-031.1 added one — `MaxAttempts: 2`, `IntervalSeconds: 60`, `BackoffRate: 2` — but its
  `ErrorEquals` lists only transport faults: `ReadTimeout`, `ConnectTimeout`,
  `ConnectionError` and four `Lambda.*` service errors. A proxy 502 surfaces as the
  `ValueError` raised by `fetch_via_proxy`, which is on none of those lists, so the
  2026-09-24 run got **one attempt** and died — the deployed ASL confirms it. Adding
  `ValueError` (or a dedicated exception type) would not have saved this incident, since
  eight consecutive attempts failed, but it is precisely the "occasional failures on
  protected domains" scrape.do's own error text tells you to retry.
- **The `loteria-sfn-execution-failed-prod` alarm description is now wrong.** It reads
  "Because the machine has no Retry/Catch" — stale since PR-031.1. It is the first thing an
  alert email shows, and it sent this investigation looking in the wrong place.
- **The site's sorteo links changed shape** to
  `/site/award-detail?id=292&sorteo=415&TipoSorteo=Extraordinario`. They still carry `id=`,
  so `div.container a[href*='id=']` keeps working and no change was needed — but the
  selector is now matching a URL whose meaning it does not check. A locator anchored on
  `award-detail?id=` would be narrower.
- **The prize page still ships `premiosBusqueda` as inline JS** — a parse-free feed, and
  immune to markup changes. Noted in PR-031.1, still worth doing.
