# PR-044.2 — The quarantine store

Closes **fault E**. PR-044.1 made the parser's losses *visible* (counted and logged); this
makes them *inspectable*, and fixes the file-level failure that turned one bad draw into a
weekly outage.

---

## 1. The reason-code vocabulary

Closed on purpose: `SELECT reason, count(*)` over free text is worthless.

| code | where | stored? | archive count |
|---|---|---|---|
| `section_header` | line | **no** | 9,464 (6.4964%) |
| `orphan_vendor_line` | line | yes | 0 |
| `unrecognised` | line | yes | **1** |
| `malformed_header` | file | yes | — |
| `unexpected_key` | file | yes | — |

**`section_header` is counted and never stored.** PR-044.1 measured the whole archive (118
draws, 145,680 body lines) and found 6.50% of every body is millar headings — `CENTENARES`,
`DOS MIL`, `TREINTA Y UN MIL`. Storing them would write ~9,500 rows of structure per draw,
1.1M across the archive, and bury the one row that matters.

---

## 2. What changed, and the one that is not cosmetic

**PR-035.1's defect C is fixed here.** `process_header` raises `ValueError` on a header
missing `REINTEGROS`, and until now **nothing caught it**: the exception aborted the
transform for every *other* raw file in the batch, before anything was written. One draw
with an odd header was a **full weekly outage**, not one skipped record.

Now the file is quarantined and the loop continues.

> ⚠️ **The `except` is narrow on purpose: `ValueError` only.**
> A `ValueError` here means "this input is not what the parser expects", which is exactly
> what quarantine is for. A broad `except Exception` would also swallow an S3 failure, an
> out-of-memory, or a bug in the transformer — infrastructure problems that **should** fail
> the run loudly, silently reclassified as bad data. Quarantining a genuine bug is how a
> pipeline learns to lie about its own health. `TestFailureModes::test_an_infrastructure_error_still_fails_the_run`
> pins the line.

Also: the `"Skipping file with unexpected structure"` warning now quarantines the key
instead of dropping it — the same silent-loss shape, one level up.

---

## 3. Layout and the table

```
s3://lottery-partitioned-storage-prod/quarantine/dataset=<sorteos|premios>/year=<YYYY>/sorteo=<NNNN>/<run_id>.parquet
```

`dataset`, `year` and `sorteo` are **Hive partition keys carried by the path**, not columns
in the Parquet — Glue rejects a table whose columns and partition keys overlap, and
duplicating them would defeat the partition pruning that is the only reason to lay it out
this way. `source_key` keeps each file self-describing.

All three partition keys are **`string`**, including the two that look numeric. A file that
fails *before* its header parses has no year and no sorteo, and the writer emits the literal
`unknown` rather than inventing one. The partition that says "we could not even tell which
draw this was" is precisely the one worth keeping.

`run_id` is the filename rather than a partition: a reprocessing must not overwrite the
earlier record, because the earlier record is the evidence of what the parser *used to do*.

### The table is defined, not crawled

`aws_glue_catalog_table.quarantine` in `terraform/modules/catalog/main.tf`.

Every other table in this database is discovered by a crawler. This one is not, and the
reason is PR-045.1's finding: the Silver crawlers **cannot evolve a schema**
(`UpdateBehavior = "LOG"`, `CRAWL_NEW_FOLDERS_ONLY`, partitions `InheritFromTable`). We
*define* this schema — `QUARANTINE_COLUMNS` is the source of truth — so inferring it would
add moving parts and a weekly crawler run in exchange for a known inability to follow the
very changes this table exists to record.

> The Terraform column list and `QUARANTINE_COLUMNS` are two halves of one contract.
> `TestTheSchemaMatchesTheTerraformTable` holds them together by reading the `.tf` file.

## 4. The alarms

Two, because two different things go wrong and they mean opposite things.

| alarm | fires when | means |
|---|---|---|
| `loteria-quarantined-unrecognised-prod` | a run quarantined `unrecognised` lines | the source changed shape, or the parser has a gap. **Not an outage** — the run succeeded and Silver was written |
| `loteria-quarantine-write-failed-prod` | the writer could not persist | Silver is correct, but the *record* of what was dropped is gone — fault E is back |

Both are log-metric filters over the Glue output group, the same pattern as PR-042.2's
retention alarm and for the same reason: **the failure is swallowed by design**, so nothing
else in the system will ever mention it.

> ⚠️ `QUARANTINED_UNRECOGNISED` and `QUARANTINE_WRITE_FAILED` are literal tokens the filters
> grep for. Reword either log line and nothing fails — the alarm just stops firing forever.
> A test asserts the Python constants and the `.tf` patterns match.

**The threshold is measured, and the measurement overturned the roadmap's premise.** The
roadmap assumed "the expected value is exactly zero" and asked for `> 0` rejected rows; that
alarm would have fired every Thursday and been muted inside a month. `unrecognised` fired
**once in 118 draws**, so `> 0` there is roughly an email a year.

## 5. Apply

```bash
make deploy
```

Expected: **2 Glue-catalog/alarm adds + 4 observability adds**, plus the usual build churn.
There is **no IAM change** — the Glue job role already carries `s3:PutObject` on both data
buckets because the transformer writes Silver, so `quarantine/` is inside a permission it
already had. Re-measure the plan at apply time.

> ⚠️ **Lake Formation is the thing to check after the apply**, not before. The database is
> LF-governed, and a *newly created* table does not inherit grants. If the first quarantined
> row triggers `QUARANTINE_WRITE_FAILED`, or if Athena cannot read the table, that is the
> cause:
> ```bash
> aws lakeformation list-permissions \
>   --resource '{"Table":{"DatabaseName":"lottery_santalucia_db","Name":"quarantine_rejects"}}' \
>   --query 'PrincipalResourcePermissions[].{P:Principal.DataLakePrincipalIdentifier,Perm:Permissions}'
> ```
> Writing to S3 needs no LF grant; **querying the table does.** Grant `SELECT` to whoever
> reads it. See `docs/runbooks/PR-013-lake-formation.md`.

## 6. Verify

Quarantine's normal state is **empty**, which makes it the hardest thing in this repo to
verify: "no rows" is both the success case and the case where the writer never ran.

```bash
# 1. The table exists and is queryable.
aws glue get-table --database-name lottery_santalucia_db --name quarantine_rejects \
  --query 'Table.{Cols:StorageDescriptor.Columns[].Name,Parts:PartitionKeys[].Name}'

# 2. After a run: the counters are in the log, including the zero case. This is the check
#    that distinguishes "nothing was rejected" from "the code did not run".
aws logs filter-log-events \
  --log-group-name /aws-glue/python-jobs/output \
  --filter-pattern '"quarantined"' \
  --start-time $(( ($(date +%s) - 7200) * 1000 )) \
  --query 'events[].message' --output text | tail -3
# expect a "Sorteo processed successfully into Silver" line carrying
# rejected_total / rejected_unrecognised / quarantined

# 3. Neither alarm fired.
aws cloudwatch describe-alarms \
  --alarm-names loteria-quarantined-unrecognised-prod loteria-quarantine-write-failed-prod \
  --query 'MetricAlarms[].{Name:AlarmName,State:StateValue}' --output table

# 4. If anything WAS quarantined, read it rather than clearing it.
#    (Athena; needs the LF SELECT grant from §5.)
#    SELECT dataset, sorteo, reason, line, count(*)
#    FROM lottery_santalucia_db.quarantine_rejects GROUP BY 1,2,3,4 ORDER BY 5 DESC;
#    A new partition needs MSCK REPAIR TABLE quarantine_rejects first.
```

### ✅ Result, 2026-10-08 (sorteo 3138)

The first real body through PR-044.1's counters and this PR's writer, in the scheduled run
`2417c307-…_3477d275-…a1283f3f2a4d`:

```
"Premios processed"  premios_count: 890, lines_total: 1047, lines_parsed: 967, lines_rejected: 80,
                     rejected_section_header: 80, rejected_orphan_vendor_line: 0, rejected_unrecognised: 0
"Sorteo processed successfully into Silver"  sorteo_number: 3138, rejected_total: 80,
                     rejected_unrecognised: 0, quarantined: 0
```

- **Check 2 is the one that matters, and it passed:** the counters are in the log *including
  the zero case*, so "nothing quarantined" is the writer running and finding nothing, not
  the writer never running.
- **All 80 rejects are thousand-headers** (`CENTENARES`, `MIL`, `DOS MIL` … `SETENTA Y NUEVE
  MIL`), each logged as `"Body line rejected"` with `reason: section_header`. They are
  counted and never stored, as designed, so `quarantine/` holds **0 objects**. 80 / 1047 =
  7.6%, in line with the archive's 6.50%, all of it the expected kind.
- **Check 3:** `loteria-quarantined-unrecognised-prod` and `loteria-quarantine-write-failed-prod`
  are both `OK`, unchanged since the 2026-09-27 apply. Every other alarm in the account was
  `OK` too, and the `loteria-alerts-prod` email subscription is confirmed, so the absence of
  an email is evidence rather than silence.
- Check 4 does not apply: nothing was quarantined. The write path itself remains proven only
  by the unit suite, as above — a clean draw cannot exercise it, and that is the point of
  not planting one.

**To prove the path end to end** rather than wait for a malformed draw, the honest option is
the unit suite — `TestTheWriterNeverFailsTheRun` and the two defect-C tests exercise exactly
the branches production would. Do **not** plant a broken file in `raw/` to force it: `raw/`
is the one layer that cannot be re-derived from anything (the site only shows the latest
draw), and PR-002's bucket `Deny` would not let you remove it afterwards.

## 7. What this deliberately does not do

- **No replay path.** Quarantine is not a dead-letter queue. The point is that a human reads
  it and decides whether the parser or the source changed; an automatic retry would turn
  "the site changed" into "the site changed, silently, every week". A test greps the module
  for `replay` / `reprocess` / `retry` so the decision is visible to whoever looks next.
- **The DQ gate does not read the quarantine count.** Declared as a follow-up in the roadmap
  and left there.
- **No backfill.** The archive's one historical `unrecognised` line (`00CERO`, sorteo 396)
  is not imported. Quarantine records what *this* pipeline dropped; manufacturing rows for
  draws processed before it existed would be the same lie as a backfilled `ingested_at`.
