# PR-045.2 — Make the lineage queryable

Closes the reading half of **fault F**. PR-045.1 wrote four lineage columns into every new
Silver Parquet file; this makes them answerable from Athena, and answers the question the
sub-phase exists for in one query.

Two moving parts, in this order:

| | What | Where |
|---|---|---|
| 1 | The two Silver **tables** move from crawler-inferred to **declared in Terraform**, with the four lineage columns | `terraform/modules/catalog/main.tf` — **needs an import** |
| 2 | Two **views** over them, created through Athena | `sql/lineage/`, `make lineage-views` |

Plus two type defects found on the way, both of which only become visible the moment a
schema is declared over the data — §5.

---

## 1. Why the crawlers could not do this, and why they are not being changed

PR-045.1 verified this against the live account before writing a line of code. Three
settings compound, each sufficient on its own to hide a new column:

```
$ aws glue get-crawler --name lottery-sorteos-silver-crawler
  SchemaChangePolicy.UpdateBehavior : LOG                     # detects, logs, alters nothing
  RecrawlPolicy                     : CRAWL_NEW_FOLDERS_ONLY  # never revisits a partition
  Partitions.AddOrUpdateBehavior    : InheritFromTable        # new partition gets the TABLE's schema
```

The obvious fix is to loosen them — `UPDATE_IN_DATABASE` + `CRAWL_EVERYTHING`. **That is the
wrong end to pull.** It hands the schema of the two tables seven gold CTAS queries read to a
process that re-infers it weekly from whatever landed in S3, which is how a `bigint` becomes
a `string` because one file had an odd value.

So the schema moves to Terraform and the crawlers keep the one job they are still good at:
registering the new week's partition. The three settings above stop being a defect and
become the guarantee — **a crawler that will not alter a table cannot fight a declared
schema**, and `InheritFromTable` means every partition it registers from now on is stamped
with the declared one.

The account already agreed, quietly: both tables' `UpdateTime` is **2025-12-14**, the day
they were created. The crawlers have run every Thursday for nine months and have not touched
them.

---

## 2. ⚠️ The tables must be IMPORTED, not created

A create means Glue drops and rebuilds the table Athena reads, **losing all 118 registered
partitions**. Terraform will happily plan one if the import is skipped.

```bash
cd terraform && terraform init -backend-config=backend.hcl

terraform import 'module.catalog.aws_glue_catalog_table.silver_sorteos' \
  913524903233:lottery_santalucia_db:silver_sorteos_sorteos
terraform import 'module.catalog.aws_glue_catalog_table.silver_premios' \
  913524903233:lottery_santalucia_db:silver_premios_premios
```

Then **plan and read it before applying**. The expected diff is two `update in-place`, and
nothing else from this PR:

| Change | Expected? |
|---|---|
| `columns` +4 at the end of each table (`run_id`, `ingested_at`, `source_key`, `parser_version`) | ✅ the point of the PR |
| `quarantine_rejects`: `position` and `parser_version` `int` → `bigint` | ✅ §5 |
| table `parameters`: the crawler's statistics removed (`objectCount`, `recordCount`, `sizeKey`, `averageRecordSize`, `CRAWL_RUN_ID`, `UPDATED_BY_CRAWLER`, `typeOfData`, `compressionType`, `CrawlerSchema*Version`) | ✅ deliberate — frozen at the 2025-12-14 crawl, `objectCount` says 79 against 118 partitions |
| `storage_descriptor.number_of_buckets` `-1` → `0` | ✅ cosmetic; both mean "not bucketed" |
| **anything that says `destroy`, `replace`, or touches `partition_keys`, `location`, `input_format`, `output_format` or `ser_de_info`** | ❌ **STOP.** The declaration has drifted from the account; re-read `aws glue get-table` before going further |

`classification = parquet` and `partition_filtering.enabled = true` are declared and must
stay. The second is not cosmetic: without it Athena reads every partition for a
single-sorteo lookup, which is exactly the query this PR exists to make cheap.

The usual `make build` churn (the Lambda layer, `lambda_package.zip`) shows up alongside.
Re-measure at apply time.

## 3. What was verified before the apply, and what could not be

**Verified (2026-09-28, against the live account, read-only):**

- the declared columns and types are exactly what `aws glue get-table` returns today —
  10 business columns on sorteos, 7 on premios, partition keys `year`/`sorteo`, both
  `string`;
- the two views' SQL runs, with the aggregate shape and every function in it
  (`array_agg(DISTINCT …)`, `array_sort`, `contains`) executed against the real 118
  partitions — see §6, whose output is real;
- `array_agg` **includes** NULLs, so a pre-lineage run reports `source_keys = [null]` rather
  than an empty array;
- the crawlers have not written to either table since 2025-12-14.

**Not verifiable before the apply, and therefore the first thing to check after it:** the
118 partitions registered before today carry the *old* 10-column schema, because
`InheritFromTable` stamped them with the table as it was. Athena's documented behaviour
covers this — `ALTER TABLE ADD COLUMNS` is supported for Parquet, and *"Athena relies on the
column names and uses them for its column name-based schema verification. This eliminates
`HIVE_PARTITION_SCHEMA_MISMATCH` errors for tables with partitions in Parquet"* — so the old
partitions should read the new columns as NULL. **Documented is not the same as observed.**
§4 step 1 is a five-second query that settles it, and the rollback is one revert.

```bash

# 2. ⚠️ FIRST, before anything else: can Athena still read the old partitions?

#    all seven gold CTAS, on Thursday.
#      SELECT numero_sorteo, run_id FROM silver_sorteos_sorteos WHERE sorteo = '3046';
#    expect: one row, run_id NULL. A HIVE_PARTITION_SCHEMA_MISMATCH or HIVE_BAD_DATA here
#    means revert the two table resources and re-apply — nothing else in this PR depends on
#    them staying.

# 3. The views. Needs the columns to exist, so it runs after the apply, not with it.
make lineage-views
```

`make lineage-views` is **not** part of `make deploy` and not in the Step Function: a view is
catalog metadata that does not move, and recreating it weekly would add two states to the
pipeline for nothing. Re-run it after editing `sql/lineage/`, or to restore a view somebody
dropped.

**Lake Formation needs nothing here.** `silver/` is a registered location, but the tables
already carry the grants they need and the applying principal (`angel-adming`) is a data
lake admin with `ALL` on the database and `ALL_TABLES`. This was checked, not assumed —
`lakeformation list-permissions` — because PR-042.3 and PR-042.4 were both an apply that
succeeded against a permission that had not been.

## 5. Two type defects, found by declaring the schema

Neither was reachable while nothing read the data by a declared schema. Both are the same
shape: **the bytes on disk have to match what the catalog says about them.**

### `run_id` was written as the Parquet **Null** type, not as a string

`frame["run_id"] = None` leaves an all-`None` object column, and pyarrow writes that to
Parquet as `optional int32 (Null)`. With `run_id` declared `string`, such a file is a type
mismatch — and one unreadable file is a whole partition the gold CTAS cannot read.

This is not hypothetical. PR-045.1 accepts, deliberately, that a hand-run transform without
`CORRELATION_ID` writes a NULL `run_id`; that is the gate's only way to notice something
wrote Silver outside the pipeline. Before this PR, that accepted case would also have
quietly produced an unreadable partition.

`loteria.common.quarantine` had it worse: **every** quarantine file written outside a run —
which is exactly when somebody wants to read one — would have been unreadable, and nothing
would have noticed, because quarantine's normal state is empty.

Fixed in both writers by casting to pandas `string` before the Parquet write. Pinned by
tests that fail without the cast (verified by removing it).

### `parser_version` and `position` were declared `int` over `int64` data

pandas writes a Python int as int64. Athena widens INT to BIGINT and **supports no
conversion in the other direction**, so an `int` declaration over this data is a read error
waiting for the first person to run the query. Both are now `bigint`, in the Silver tables
and in `quarantine_rejects` — corrected before that table had a single row to be wrong
about.

## 6. The question this sub-phase exists for

> *"Sorteo 3134 looks wrong — which run wrote it, from which raw file, and what else did
> that run write?"*

```sql
SELECT * FROM silver_lineage_runs WHERE contains(sorteos, '3134');
```

Real output, **2026-09-28, before the apply** — run as an inline `WITH` against the live
tables with the four not-yet-catalogued columns substituted as typed NULLs, which is as close
as it can be taken until the first lineage-carrying draw lands:

```
dataset | run_id | rows_written | sorteos_written | first_ingested_at | source_keys | sorteos_sample
premios | NULL   | 124447       | 118             | NULL              | [null]      | [3046, 3047, 3048, 3049]
sorteos | NULL   | 118          | 118             | NULL              | [null]      | [3046, 3047, 3048, 3049]
```

That is the correct answer today and it is worth reading carefully: **every row in Silver was
written before lineage existed**, so they all belong to the one NULL run, and the query
truthfully says so. `run_id NULL` is not a gap in the view — it means *written before
lineage existed*, and it is deliberately not backfilled (PR-045.1 §6: a fabricated `run_id`
claims a provenance nobody recorded).

The per-sorteo view answers the narrower half:

```sql
SELECT * FROM silver_lineage WHERE sorteo = '3134';
```
```
dataset | run_id | parser_version | year | sorteo | source_key | rows_written
premios | NULL   | NULL           | 2026 | 3134   | NULL       | 894
sorteos | NULL   | NULL           | 2026 | 3134   | NULL       | 1
```

Both queries scanned **0 bytes**: `count(*)` comes from the Parquet footer and the lineage
columns were constants. After the first real run they read four actual columns, so the cost
becomes Athena's 10 MiB minimum per query — the floor PR-043.1 measured, at which the whole
gold rebuild costs $0.019 a year.

## 8. What this PR deliberately does not do

- **No backfill.** Unchanged from PR-045.1, and now visible in the view as the NULL run.
  A sentinel `backfill-PR-045` run_id across 222 rewritten files stays a separate PR, to be
  decided on its own merits.
- **No `run_id` in Gold.** The roadmap recommends `gold_draw_summary` should carry the run
  that built it, and it needed the catalog to expose the column first — which is now true.
  It is a change to a gold CTAS and to seven files' worth of precedent about what a gold
  table contains, so it gets its own PR rather than riding in on this one.
  `TestGoldCannotInheritSilverColumnsByAccident` still holds: no gold file uses `SELECT *`.
- **No crawler change.** See §1. Their settings are now load-bearing in the opposite
  direction, which is worth remembering before anyone "fixes" them.
- **The views are not in Terraform.** An Athena view is stored as a base64 blob of Athena's
  internal JSON, carrying the SQL *and* a column list that must agree with it. Hand-writing
  that in Terraform means maintaining an undocumented serialisation — and it drifts: the
  views already in this account carry `isProtected` and `isMultiDialect` keys that the
  widely copied Terraform examples do not have. A table's schema is ours to declare; a
  view's encoding is Athena's. See `sql/lineage/README.md`.
