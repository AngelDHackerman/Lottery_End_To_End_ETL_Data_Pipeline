# PR-031.1 — Restore the scraper: Cloudflare bypass, new prize markup, retries

**Unplanned fix, not a roadmap item.** The weekly pipeline stopped ingesting data on
2026-08-20. Two runs failed (2026-08-20 and 2026-08-27), both ~26 s in, both at
`RunExtractorLambda`. This PR restores extraction and closes the observability gaps that let
the outage run for two weeks with one alarm still green.

**Nothing is corrupt.** Both runs died at step 1, so Glue, the crawlers and the gold CTAS
never executed and no partial writes exist. The lake is simply stale: raw stops at
`raw/sorteo_3132.txt` (110 objects), silver at `silver/sorteos/year=2026/sorteo=3132/`, gold
was last rebuilt 2026-08-13 15:12.

---

## 1. Two independent failures, found in this order

### 1a. Cloudflare stopped accepting the proxy profile

Production called scrape.do with `geoCode=MX` and nothing else. Every request now returns
`502 / ErrorCode 90 / ErrorType ROTATION_FAILED`, message `"cannot connect target url"`,
after **~57 s**.

That message is misleading and cost real diagnosis time. It is **not** an unreachable host
and **not** IP-reputation packet dropping — it is scrape.do's plain HTTP client failing
Cloudflare's browser check. Two observations separate those cases:

- direct `curl` from a laptop and from a datacenter both get a **fast HTTP 403** block page
  ("Sorry, you have been blocked"), in ~0.1 s — Cloudflare answers;
- scrape.do gets **no response at all** until its own internal give-up at 57 s.

The site's DNS, IPv4 reachability and the scrape.do account were all ruled out: the A record
resolves and answers, the token is valid, the plan is active, and fetching *any other* site
through the same proxy returns 200 in 1.7 s.

**The working profile needs three parameters together.** Every proper subset was tested
against the live site on 2026-08-27 and every one still failed:

| Attempt | Result |
|---|---|
| `geoCode` plain: AR, BR, CL, CR, US, MX | `ROTATION_FAILED` |
| `super=true` + GT / MX / CO / SV | `ROTATION_FAILED` |
| `render=true` alone | `ROTATION_FAILED` |
| `render` + `geoCode=MX` | `ROTATION_FAILED` |
| `render` + `geoCode=GT`, no `super` | `ROTATION_FAILED` |
| `render` + `super`, no `geoCode` | `ROTATION_FAILED` |
| **`render=true` + `super=true` + `geoCode=GT`** | **HTTP 200 in ~5-6 s** |

So the country does matter — Guatemala specifically, and only in combination with
residential IPs and headless rendering. `GT` is not offered on datacenter proxies at all.
(The docs' datacenter country list is incomplete, incidentally: `MX` is absent from it yet
demonstrably works.)

### 1b. The site moved the prize list

Independent of the proxy, the extractor would now have written **garbage without failing**.
It read `soup.select("div.card-body div.row")[2]`. On the redesigned page that div holds
~358 characters of legal boilerplate, and there are still exactly three rows — so the
`len(rows) < 3` guard passed. The run would have gone green with a prize-less raw file.

Current layout:

| Element | Content |
|---|---|
| `row[0]` | the ticket search box |
| `row[1]` | `<div id="div_resultado">`, empty until a visitor searches |
| `row[2]` | legal boilerplate ("ESTIMADO PUBLICO…") |
| **`div.lista-premios-columnas`** | **the prizes** — ~900 `div.premio-item` children |

Extracting the new container yields **1056 lines** against 1059 in the historical
`raw/sorteo_3132.txt` — same structure, padded with extra internal whitespace (73 KB vs
25 KB), which this PR collapses so the archive stays homogeneous.

**`parser.py` needs no change.** Its prize-line regex (`parser.py:89`) matches on `\s+` and
absorbs the padding, and section labels like `MIL` fall through every branch harmlessly.
Verified against the real page before writing any code.

## 2. What changed

| File | Change |
|---|---|
| `src/loteria/extractor/scraping.py` | `build_proxy_url()` (new, testable) emitting `render`+`super`+`geoCode=GT`; timeout 25 s → 60 s; metric on the exception path; `extract_prize_body()` (new) replacing the positional row index. |
| `src/loteria/common/metrics.py` | `record_scraper_no_response()` + `STATUS_NO_RESPONSE`. |
| `terraform/modules/etl-lambda/main.tf` + `variables.tf` | Four `SCRAPE_*` env vars so the profile is tunable without rebuilding the zip. |
| `terraform/modules/orchestration/main.tf` | `Retry` on `RunExtractorLambda`. |
| `tests/unit/test_scraping.py` | **New.** 16 tests. |
| `tests/fixtures/sorteo_page_2026_08.html` | **New.** Trimmed, anonymized capture of the redesigned page. |
| `tests/integration/test_scraper_contract.py` | Canary follows the same proxy profile; asserts the new container; fails (not skips) on a hard block page. |

### The alarm that stayed green

`loteria-scrapedo-failed-prod` sat in `OK` for the entire outage.
`record_scraper_status(resp.status_code)` can only be called once a response object exists,
so a `ReadTimeout` — the exact shape of this outage — emitted **nothing**. The metric
`ScraperHttpStatus` has only ever recorded dimension value `200` in its life.
`record_scraper_no_response()` closes that hole, emitting `StatusCode=NoResponse` plus the
dimensionless `ScraperHttpErrors` the alarm already watches. **No alarm or dashboard change
is needed** — the new datapoint lands on the series they already use.

### The timeout was hiding the evidence

`timeout=25` sat *below* scrape.do's own ~57 s give-up, so production never saw the real
`502 ROTATION_FAILED` — only a local `ReadTimeout`. That is why the logs named the wrong
cause for two weeks. 60 s lets the true error surface and still leaves room for two calls
inside the Lambda's 120 s ceiling (a rendered success takes ~5-6 s).

### Retry — and honestly, what it does not fix

`RunExtractorLambda` had no `Retry` at all: one attempt, and a once-weekly execution died
for the whole week with nothing going back for the missed sorteo.

The error list is explicit rather than `States.ALL` because **a retry is no longer cheap**
(see §3). Retrying a deterministic bug — a missing selector, a parse failure — would burn
150 credits to fail three times instead of once. Only transient faults are listed.

Retrying is safe: `extract_lottery_data()` calls `check_if_sorteo_exists()` and returns
without writing when the sorteo is already in S3.

**This would not have saved the two failed runs.** The Cloudflare block was persistent, not
transient. No `Catch` was added either: on final failure the desired behaviour *is* for the
execution to fail, which `loteria-sfn-execution-failed-prod` already watches. A catch-to-fail
state would be ceremony.

## 3. Cost — this is the part to watch

**25 credits per successful request**, measured by diffing `RemainingMonthlyRequest` across a
call. It was 1. The plan is **1000/month**.

| | Requests | Credits |
|---|---|---|
| One pipeline run | 2 (listing + detail) | **50** |
| Weekly cadence | ~8.6/month | **~215/month** |
| Worst case with retries | 6 | 150 |
| Live canary run (PR-031, weekly) | 2 | 50 |

That is ~26% of quota for the pipeline alone, before the canary. It fits, but it is no longer
negligible — **do not raise the trigger frequency without redoing this arithmetic**, and
treat a quota exhaustion (`402`) as a plausible future failure mode rather than a theoretical
one.

**Failed requests are not charged.** A full quota counter is therefore *not* evidence the
pipeline ran — during this outage the counter read a pristine 1000/1000.

Other plan limits worth knowing: **5 concurrent requests**; a parallel burst returns
`429 "You are sending too fast request"`.

## 4. Apply

No imports, no state operations. `make build` **must** run first — `filemd5` /
`filebase64sha256` read the zips at plan time, so a stale artifact fails the plan itself.

```bash
make build
cd terraform
terraform plan -out=tfplan     # expect: 0 add, 2 change, 0 destroy
terraform apply tfplan
```

The two in-place updates are `aws_lambda_function.extractor_lambda` (new code + the four
`SCRAPE_*` env vars) and `aws_sfn_state_machine` (the `Retry` block).

⚠️ **Merging is not applying, and the zip re-upload is the step that gets skipped.** This has
bitten this repo before (see PR-019's notes): the extractor ran three PRs behind for weeks
because the artifact was never rebuilt. The code change in this PR is the entire fix — if the
zip is not rebuilt and uploaded, the pipeline stays broken while the plan looks clean.

## 6. Follow-ups filed, not fixed here

- **A cleaner data source exists.** The detail page ships a 52 KB inline JS object,
  `premiosBusqueda = {"00068":{"monto":800,"vendidoPor":""}, …}` — number → amount + vendor,
  already structured. Parsing that instead of the DOM would make the extractor immune to the
  class of redesign that caused §1b.
- **Single point of failure unchanged.** One run per week against a site actively hardening
  against scrapers. The retry helps with blips, not with the next profile change.
- **The token travels in the URL query string.** scrape.do's API design, but it means the
  token appears in `ps` output and in any request logging. Rotate it if that matters.
